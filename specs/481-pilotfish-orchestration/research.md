# Phase 0 Research: Pilotfish-Style Cost-Tiered Model Orchestration

All spec-level `[NEEDS CLARIFICATION]` markers were resolved in `/speckit-clarify`
(Session 2026-07-09). This file resolves the remaining **implementation** unknowns from the
plan's Technical Context, grounded in the actual repo state (checked 2026-07-09).

## R1 — Toggle wiring pattern

**Decision**: Follow the **skillclaw opt-in pattern** exactly. Add `ENABLE_PILOTFISH=false`
(default) + `PILOTFISH_SET=false` in `bootstrap/lib/config.sh`; add `--enable-pilotfish` /
`--disable-pilotfish` to the arg parser and `--help` usage; add a `pilotfish:` section to the
`write_services_config()` heredoc with `enabled: ${ENABLE_PILOTFISH:-false}`; extend the
services.yml→FILE_* awk parser to emit `FILE_PILOTFISH=true|false`.

**Rationale**: `services.yml` is generated by the `write_services_config()` heredoc in
`bootstrap/lib/config.sh`; the committed `configs/claude/config/services.yml` copy must stay in
lock-step (a `bootstrap_services.bats` gate diffs them — issue #460), so the `pilotfish:` block is
added to BOTH. skillclaw is already `enabled: ${ENABLE_SKILLCLAW:-false}` with
`ENABLE_SKILLCLAW=false` — a proven, opt-in-by-default toggle identical in shape to what pilotfish
needs (spec Assumptions: default disabled).

**Toggle persistence across default runs**: like the other integrations, a default bootstrap (no
`--enable/--disable-pilotfish`) does NOT force the toggle to false — the merge-precedence block
(`if [[ "$PILOTFISH_SET" == false && -n "$FILE_PILOTFISH" ]]; then ENABLE_PILOTFISH=$FILE_PILOTFISH; fi`,
config.sh) reads the existing `services.yml` value first, so a previously-enabled integration
stays enabled across re-runs (Principle V, Bootstrap Reproducibility). `PILOTFISH_SET=true` only
when the user passes an explicit flag, which then wins.

**Alternatives considered**: graphify pattern (`ENABLE_GRAPHIFY=true`, on by default) —
rejected: the spec defaults pilotfish to opt-in, matching skillclaw not graphify.

## R2 — Role → model mapping (built-in aliases, corrected by product spec-review)

**Decision**: Each role frontmatter names a **Claude Code built-in model alias**
(`haiku`/`sonnet`/`opus`) directly — NOT a custom tier name and NOT a raw model ID:

| Role | `model` alias | Resolves to (current) | `effort` |
|------|---------------|-----------------------|----------|
| scout | `haiku` | Haiku 4.5 | low |
| Explore | `haiku` | Haiku 4.5 | low |
| mech-executor | `sonnet` | Sonnet 5 | low |
| executor | `opus` | Opus 4.8 | medium |
| verifier | `opus` | Opus 4.8 | medium |
| security-executor | `opus` | Opus 4.8 | high |

The orchestrator/"frontier" model is the **unchanged main session** (R7/FR-016), not a role and
not a deployed alias.

**Rationale**: The **product spec-review (2026-07-09) CONFIRMED** that the earlier custom
four-tier alias layer (`best`/`high`/`mid`/`cheap`) had no runtime resolution path — Claude
Code agent frontmatter `model:` accepts only its built-in aliases (`haiku`/`sonnet`/`opus`),
`inherit`, or a full model ID; a custom name would fail to resolve and break the role-agent.
Binding roles to built-in aliases (a) resolves natively with **no** deployed alias file and
**no** `settings.json` change (which R7/FR-016 forbid anyway), (b) satisfies FR-002 (aliases,
not raw IDs), and (c) makes pin reconciliation automatic: the built-in aliases already float to
Manifest's current pins (`opus`→Opus 4.8, `sonnet`→Sonnet 5, `haiku`→Haiku 4.5). This is also
how pilotfish itself pins roles (only its `best` main-session alias was custom, and we don't
adopt it). Model availability/fallback (FR-007) is Claude Code's responsibility for built-in
aliases — no custom fallback chain is deployed.

**Alternatives considered**:
- Custom tier aliases (`best/high/mid/cheap`) resolved via a deployed settings file (the
  reviewer's suggested direction) — **rejected**: Claude Code does not resolve custom
  frontmatter model names, and it would reintroduce the `settings.json` mutation FR-016/clarify
  -Q1 rejected (and the deploy-clobbers-settings risk).
- Hard-coding full model IDs per role — rejected (FR-002; every model-version change would touch
  six files). A per-role pin override to a full ID remains available as a documented single-
  point exception when a specific version is genuinely required.

## R3 — Deploy mechanism: gate-deployed `agents/` dir, clean disable, collision-abort

**Decision**: **Exclude both `configs/claude/agents/` AND
`configs/claude/references/pilotfish-delegation.md` from the wholesale rsync** (like `/skills`)
and let the gate be the sole deployer of both — so a disabled/foreign run never lands either, and
there is no copy-then-delete churn on default bootstraps. The two helpers live in
`bootstrap/lib/common.sh`, invoked from `deploy.sh`:
- **Pre-rsync guard** `check_pilotfish_collision` (before any destructive copy): abort non-zero,
  naming the file, only if `~/.claude/agents/` lacks the marker AND already holds a file whose
  name is one of the **six** pilotfish role files (FR-008). A differently-named user agent is not
  a collision, so a disable that left one behind cannot deadlock the next enable.
- **Post-copy gate** `gate_pilotfish_agents "$home" "$src_agents"`: when `FILE_PILOTFISH=true`,
  `mkdir` the dir, copy the six role files **and the reference** from source (the reference source
  is the `references/pilotfish-delegation.md` sibling of `$src_agents`), **write** the `.pilotfish`
  marker, and inject the delegation pointer into the deployed guide (idempotent — cp overwrites
  our own files, the marker is re-stamped, the inject is grep-guarded). When `false`,
  manifest-scoped prune (remove `PILOTFISH_AGENT_FILES` + marker + reference + pointer, `rmdir`
  only if empty), preserving a coexisting user agent (SC-003, FR-006).

**Rationale**: a **shipped** `.pilotfish` marker in the rsync stream would make "Manifest-owned"
read true after *any* deploy — even a disabled one — so a default (disabled) `bootstrap.sh` run
would copy the marker + role files and then the disable prune would delete a user's same-named
`~/.claude/agents/scout.md` (data loss on the default path). Excluding `agents/` from rsync and
making the gate the sole writer of the marker + files removes that hazard: the marker exists only
when we deliberately deploy it, so a disabled or foreign home is never touched. The gate-function
shape already exists for skills (`gate_graphify_skill`); this is the agents-dir analogue.
Abort-not-clobber matches Principle V and the clarify answer (Q3).

**Case-insensitive filesystem note (macOS APFS default)**: the six-name check uses `[[ -e
"$agents/$name" ]]`, which the OS resolves case-insensitively — so a user's `explore.md`
(lowercase) IS detected as colliding with our `Explore.md` and aborts (the guard fires). On a
case-sensitive filesystem the two are distinct files, so the gate's `cp Explore.md` creates a
separate file and never overwrites the user's `explore.md`. Either way there is no silent
clobber, so no case-folding normalization is needed.

**Alternatives considered**: (a) rsync-wholesale + post-copy prune (the original design) —
**rejected**: a disabled default run copies then prunes the marker, deleting a same-named user
agent (found by technical spec-review). (b) skip-colliding-and-continue / backup-then-overwrite —
rejected by the clarify decision (partial deploys and surprising mutation of foreign config).

## R4 — Gate compliance: naming taxonomy + derived-doc drift

**Decision**: No changes needed to the naming gate or derived-doc generators; add coverage
that confirms they stay green.

**Rationale**: `skill_naming.bats` scans **only** `.skillshare/skills/` (`SKILLS_DIR`,
line 13) — it does not scan `configs/claude/agents/`, so the six agent filenames (scout.md,
Explore.md, mech-executor.md, …) do not trip the `<purpose>-<verb>` taxonomy. `generate_
cursor_rules.sh` and `generate_commands_doc.py` derive from skills, not agents, so the new
files produce no COMMANDS.md / cursor-rule drift. The one always-loaded surface that changes is
the single Reference Index pointer line in `configs/claude/CLAUDE.md` (see R5).

**Alternatives considered**: registering agents in `command_config.yml`/`command_categories.yml`
— rejected: agents are not skills/commands and those catalogs are skill-scoped.

## R5 — Budget-safe policy placement

**Decision**: The full delegation policy (role→built-in-alias table, escalation rules,
selective-verify rule, security-routing rule, attribution) lives in
`configs/claude/references/pilotfish-delegation.md` (read-on-demand, deployed to
`~/.claude/references/`). The pointer line is **injected into the deployed guide** at deploy
time (it is NOT committed to `configs/claude/CLAUDE.md`, keeping the source pointer-free). A bats
assertion confirms the **deployed** guide — committed source **plus** the injected pointer —
stays under the `context_budget.bats` cap (7400), so enabling can never push the always-loaded
guide over budget.

**Rationale**: FR-014 + the token-economy rule: full detail belongs in on-demand references,
never in Claude auto-loaded guides. The source guide had only 3 bytes of headroom, so the
injected ~120-byte pointer overflowed the deployed guide (7547 > 7400) — caught by the new
source+pointer budget test. Room was reclaimed by **condensing** the verbose "ALWAYS Use Parallel
Agents For" sub-bullet lists in the guide to inline lists (lossless; the same condensation was
applied to `configs/gemini/GEMINI.md` to keep the sibling guides in sync — Cursor's was already
condensed), bringing source to ~7213 and the deployed guide to ~7333 (67-byte margin). This is
the "trim an adjacent line, documented, not a cap raise" reclamation this section anticipated.

**Alternatives considered**: inline the policy into CLAUDE.md (max discoverability) — rejected
by FR-014 and the budget cap. A dedicated always-loaded section — same rejection.

## R6 — Reconcile/prune interaction (corrected by technical spec-review)

**Decision**: No reconcile change is needed. `deploy_reconcile` lists orphans only within the
`skills`/`config` units — it does **not** scan `~/.claude/agents/` at all — so neither the
deployed role files nor a coexisting user agent are ever flagged or pruned by reconcile.
Ownership + toggle removal are handled entirely by the gate: the `.pilotfish` marker identifies
the Manifest-owned dir, and the disable path does a **manifest-scoped prune** (remove only
`PILOTFISH_AGENT_FILES` + marker, `rmdir` only if empty).

**Rationale**: Verified against `configs/claude/scripts/deploy_reconcile.sh` (header: "Lists
deployed units (skills/config)…"). An earlier assumption that reconcile would treat the whole
`agents/` dir as owned was wrong; **the technical spec-review flagged the corollary risk** — a
`rm -rf agents` disable would delete a user-authored agent. Fixed: the disable path is
manifest-scoped (mirrors `deploy_home_skills`' preserve-foreign behavior), so a coexisting user
agent survives (FR-006), and the collision guard keys on the marker so an enabled re-run is
idempotent (FR-008/Principle V).

**Alternatives considered**: register the whole `agents/` dir as a reconcile-owned unit —
rejected: reconcile does not scan `agents/`, and a whole-dir prune would delete user agents.

## R7 — Not changing the main-session model (FR-016)

**Decision**: The integration deploys role-agents + the policy reference **only** (roles use
built-in aliases, so no alias-definition file is deployed — see R2). It does **not** modify the
deployed `settings.json`/`settings.local.json` main-session `model` field or its fallback, and
does **not** touch `merge_claude_settings_defaults`. The orchestrator/frontier model is
documented in the policy as "the session's frontier model" — whatever the user already runs —
rather than being forced via a settings alias.

**Rationale**: Clarify decision Q1 (user asked for the recommendation → agents+policy only).
`merge_claude_settings_defaults` is a user-wins snapshot/union path (deploy-clobbers-settings
note); writing a `best` alias there would risk clobbering user model choices and collide with
Manifest's pins. Claude Code already runs the frontier model as the session default, so the
Layer-1 settings change buys little for real blast radius.

**Alternatives considered**: full pilotfish Layer 1 (`best` alias + `[opus,sonnet]` fallback in
settings.json) — rejected by Q1; larger blast radius, settings-merge conflict risk.

## R8 — Upstream attribution + drift strategy (FR-011)

**Decision**: Vendor-and-adapt. Record the upstream source, license (MIT), and the exact
vendored version (pilotfish v1.1.0, commit/date) in a header comment in
`pilotfish-delegation.md` and in a NOTICE/attribution line in the docs. Drift is managed by
that recorded version + periodic manual review (no automated upstream sync).

**Rationale**: Spec Assumptions + FR-011. Manifest already vendors external ideas into its own
config and owns gate compliance/model-pin reconciliation; a hard dependency on pilotfish's
upstream installer would fight Manifest's config-as-code + bootstrap deploy model (Principle I).

**Alternatives considered**: depend on upstream installer / git submodule — rejected: conflicts
with reproducible bootstrap deploy and Manifest's model-pin reconciliation ownership.
