# Feature Specification: APM-Based Deploy Pipeline (Drift Elimination)

**Feature Branch**: `522-apm-deploy-migration`

**Created**: 2026-07-25

**Status**: Draft — revised after five adversarial reviews (four independent critics + the parallel-agent panel)

**Input**: User description: "Would it make sense to migrate this repo to a Claude plugin structure AND/OR Microsoft APM?" → refined to: replace the hand-rolled generate-and-rsync deploy pipeline with a lockfile-backed, hash-tracked package installer so every assistant home is a reproducible build output rather than accumulated state. Distribution model subsequently decided by the maintainer: **published packages**.

## Overview *(context — non-normative)*

Manifest deploys agent configuration into five assistant homes (`~/.claude`, `~/.cursor`, `~/.gemini`, `~/.codex`, `~/.antigravity`) via `bootstrap.sh`, which **rsyncs a generated tree into live, user-mutated directories while keeping no record of what it previously wrote**. Bespoke generators produce derived artifacts — 109 `.mdc` rule files plus the COMMANDS/GEMINI/AGENTS guides — committed alongside their sources and regenerated by hand.

That architecture produces three distinct, repeatedly-observed failure classes:

| Class | Definition | Observed instances |
|---|---|---|
| **Generation drift** | Committed derived artifacts diverge from their sources | end-of-file-fixer fighting the generated `.mdc` double-newline; a merged skill count leaving `COMMANDS.md` stale |
| **Deploy drift** | The live home tree diverges from what the repo would produce | rsync clobbering user-added `mcpServers` in `settings.local.json`; `deploy_home_skills` copying skills whose service toggle is off; work stranded "blocked on `~/.claude` redeploy" |
| **Orphan drift** | Files a prior deploy wrote are never removed | a renamed skill's `__pycache__` tripping the naming gate locally while CI stayed green; `~/.cursor/rules` never pruned; `deploy_reconcile.sh` existing at all |

All three trace to one missing property: **the deployer has no manifest of what it owns.**

### The generators are not one class

This distinction is load-bearing and was wrong in the first draft:

| Script | Kind | Disposition |
|---|---|---|
| `generate_cursor_rules.sh`, `generate_cursor_agents.py`, `generate_cursor_mcp.py` | per-harness compile of source primitives | **In scope** — replaceable by a harness-targeted build |
| `deploy_reconcile.sh` | orphan reconciliation | **In scope** — superseded by drift detection |
| `generate_commands_doc.py` | renders `docs/COMMANDS.md`; injects an index into `configs/gemini/GEMINI.md` and `AGENTS.md` | **Out of scope — no equivalent exists.** It produces *repository documentation*, not per-harness deploy config, and the build tool's own target matrix states no target generates catalog/documentation indexes. It **stays on the legacy pipeline**; US2's "no hand-run generator" claim explicitly does not cover it |
| `sync-skills.sh` | **live contributor CLI** installed to `~/.local/bin`, run ad hoc as the daily skill-dev workflow | **In scope but not as a generator** — it is a *second live writer* of the same paths. Treated as a deployer under FR-027, never as a build step |

**Microsoft APM** (`microsoft/apm`, MIT) — *Agent Package Manager*, not Application Performance Monitoring, which is the other live meaning of "APM" in this repository's tooling guidance — is a dependency manager for agent primitives that supplies the missing ownership manifest. Its install records **per-file content hashes in a lockfile**, removes files a package previously produced but no longer does, and **retains user-edited files** rather than overwriting them. Its `--target` list is a superset of Manifest's five harnesses, and `apm audit` detects drift.

This feature adopts APM as Manifest's **build and deploy layer** for configuration content. CLI installation, OAuth, MCP configuration, service toggles, and the settings merge have no APM equivalent and remain in `bootstrap.sh`, which narrows to those responsibilities.

**A Claude plugin is not an alternative — it is a potential output** (`apm pack` bundles a package as a plugin). Plugin packaging is an explicitly optional, deferrable story (US4).

## Clarifications

### Session 2026-07-25

- Q: APM or Claude plugin? → A: **APM as the build/deploy layer; the Claude plugin is a downstream artifact of it (`apm pack`), not a competing migration.** A plugin covers one of five harnesses and cannot carry permissions/env settings.
- Q: Big-bang migration or incremental? → A: **Parallel-run.** A legacy generator is deleted only after its APM-produced output matches on two independent clean runs.
- Q: What happens if the feasibility spike fails? → A: **Documented NO-GO is a valid, successful outcome.** No Manifest source is restructured before the spike returns GO.
- Q: Clone-and-build, or publish-and-install? → A: **Published packages.** Manifest is published as an APM package and installed by name; machines do not deploy from a local checkout. This is a maintainer decision, not a spike output — the spike now *verifies* the published path rather than choosing between paths. **Consequence: remote resolution is inherent, so integrity verification, pre-publish scrubbing, an offline path, and a publish-free local development loop all become mandatory (FR-018, FR-029 – FR-032), not optional.**
- Q: How are plugins organized and named? → A: **Compartmentalized by domain, every plugin prefixed `manifest-`.** See FR-025/FR-026 and the flagged naming trade-off in Assumptions.
- Q: The constitution names `bootstrap.sh` as the sole deployer — amend or violate? → A: **Amend, mechanism-neutrally.** Principles I and V were redefined as *properties* of deployment rather than named scripts, and Principle VII (Published Artifact Integrity) was added. Constitution v2.0.0. The amendment presupposes no spike outcome and names no tool, so it is valid under GO or NO-GO.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A home deployment is reproducible and self-cleaning (Priority: P1) 🎯 MVP

A maintainer changes a skill, publishes, deploys, and the live home tree ends up **exactly** as the lockfile describes — the change present, files the previous deploy wrote but the current source no longer produces gone, and a config file the user hand-edited preserved rather than silently overwritten. Running the deploy again changes nothing.

**Why this priority**: This is the entire thesis. All three drift classes are either eliminated for the migrated slice or the approach is disproven. Demonstrable against a single harness, so it is a genuine MVP.

**Independent Test**: In an isolated `HOME`, install a two-primitive published package; assert the deployed tree is **non-empty and matches an expected file manifest**; rename a primitive, republish, re-install; assert the old file is gone (having first asserted it was present), the new file is present, no orphan remains, and a hand-edited file survived and is reported. Re-run install and assert a byte-identical tree.

**Acceptance Scenarios**:

1. **Given** an isolated `HOME` with no prior Manifest state, **When** the deploy runs from the published package and lockfile alone, **Then** the resulting home tree matches the expected manifest exactly, with no manual steps.
2. **Given** a deployed home tree in which a file is known present, **When** its source primitive is renamed and the deploy re-runs, **Then** the old file is removed and no orphan directory or cache artifact remains.
3. **Given** a deployed home tree in which the user has hand-edited a deployed file, **When** the deploy re-runs, **Then** that file is retained **and surfaced to the user within the deploy workflow**, not silently kept.
4. **Given** a completed deploy, **When** the deploy runs again with no source change, **Then** the home tree is byte-identical and the run reports no changes.
5. **Given** a deployed home tree, **When** the drift-detection command runs, **Then** it reports drift if and only if the tree diverges from the lockfile.

---

### User Story 2 - One source tree builds every harness (Priority: P2)

A maintainer edits a skill once and every harness — Claude, Cursor, Gemini, Codex, Antigravity — receives its correct, harness-shaped output from a single build, with no hand-run per-harness generator and no committed derived artifacts to keep in sync.

**Why this priority**: Eliminates generation drift, the class a Claude plugin cannot touch at all, and retires four bespoke scripts plus 109 committed `.mdc` files. Depends on US1 proving the mechanism.

**Independent Test**: Edit one skill; run a single build; confirm every harness's output reflects the edit, equals what the legacy generators produce for identical input on two independent clean runs, **and is functionally consumed by at least one real harness** (content-equal is not behavior-equal).

**Acceptance Scenarios**:

1. **Given** a single edited source primitive, **When** one build runs, **Then** each configured harness target receives correct output without any additional per-harness generator invocation.
2. **Given** the legacy generators and the new build run on identical input, **When** their outputs are compared, **Then** they are equivalent (modulo documented, intentional differences), on two independent clean runs.
3. **Given** the new build is authoritative for a harness, **When** the corresponding legacy generator and its committed derived artifacts are removed, **Then** the repository's verification suite still passes.
4. **Given** a harness excluded from the build tool's default target set, **When** the build runs, **Then** that harness is still produced because it is named explicitly.
5. **Given** `generate_commands_doc.py` has no build-tool equivalent, **When** US2 completes, **Then** that script and its documentation outputs remain on the legacy pipeline, stated plainly rather than silently omitted.

---

### User Story 3 - `bootstrap.sh` narrows to what only it can do (Priority: P3)

A user runs one setup entry point and still gets a working machine — CLIs installed, authentication checked, MCP servers configured, service toggles honored — but the configuration-content half of that script is gone, delegated to the package installer, with the boundary documented and diagnosable.

**Why this priority**: Realizes the maintenance payoff and prevents a permanent two-deployer state, which is worse than either pipeline alone.

**Independent Test**: On a clean machine run the single setup entry point; confirm a working environment; confirm `bootstrap.sh` deploys no configuration content for any migrated domain; confirm the diagnostic reports which pipeline owns what.

**Acceptance Scenarios**:

1. **Given** a clean machine, **When** the user runs the documented setup entry point, **Then** they reach a working environment without needing to know two mechanisms exist underneath.
2. **Given** a migrated content domain, **When** `bootstrap.sh` or `sync-skills` runs, **Then** neither deploys that domain, so no file has two writers.
3. **Given** a partially migrated machine, **When** the environment diagnostic runs, **Then** it reports which pipeline owns each deployed area and flags any area claimed by both.
4. **Given** the service toggles gating optional components, **When** a component is disabled, **Then** it is **absent** from the home tree after deploy, as today.

---

### User Story 4 - Compartmentalized `manifest-` plugins (Priority: P4, optional)

A user installs Manifest's Claude-facing configuration as **several domain-scoped plugins rather than one monolith**, each prefixed `manifest-`, and enables only the domains they want.

**Why this priority**: Genuine benefit (per-domain enable/disable, provenance from the name) but strictly additive. US1–US3 deliver the full drift fix. Droppable without reopening the spec.

**Independent Test**: Install one `manifest-` plugin into an isolated `HOME`; verify only that domain's components appear, every Manifest plugin carries the `manifest-` prefix, disabling removes exactly its own components — **and that the enabled domain still functions with its sibling domains disabled** (see FR-028).

**Acceptance Scenarios**:

1. **Given** a published package, **When** a user installs it by name on a clean machine, **Then** they receive the same configuration surface as a full install.
2. **Given** the compartmentalized plugin set, **When** a user enables exactly one `manifest-` plugin, **Then** only that domain's skills and agents become available.
3. **Given** any Manifest-published plugin, **When** it is listed in `/plugin`, in `enabledPlugins`, or referenced by a scoped component name, **Then** its name begins with `manifest-`.
4. **Given** an enabled `manifest-` plugin whose skills depend on shared scripts, **When** sibling plugins are disabled, **Then** the enabled plugin's skills still execute successfully.

### Edge Cases

- **Feasibility spike returns NO-GO**: The feature MUST stop at a documented decision record; no Manifest restructuring occurs. NO-GO is a successful completion of the spike.
- **The MVP domain already has two writers**: `deploy_home_skills()` (called by every `./bootstrap.sh`) and `sync-skills.sh` (installed to `~/.local/bin`, the documented daily skill-dev workflow) both write `~/.claude/skills` — the exact domain US1 targets. Unless both are gated *before* the first APM-managed domain ships, an ordinary contributor action re-clobbers APM-owned files using a different ownership model. This is a defect created by sequencing, not by accident (FR-027).
- **Skills are symlink-shared across four harnesses today**: `link_shared_assets()` symlinks Cursor/Gemini/Codex/Antigravity skill directories to `~/.claude/skills` — one physical copy, four consumers. A per-target compiled build produces independent copies, quintupling files and allowing per-harness divergence that is impossible today. Which model wins MUST be decided explicitly (FR-033).
- **A deployed file is mutated by Manifest's own installer, not a human**: `install_issue_hooks.sh` flips keys in the *deployed* `command_config.yml`, and `preserve_issue_sync_gates()` exists to carry that across redeploys. Under file-level user-edit retention, the first issue-hook opt-in would look like a permanent hand-edit — freezing the file and emitting a standing warning forever. Scripted mutation must be distinguishable from human edit (FR-034).
- **Concurrent worktrees share one real `HOME`**: Multiple checkouts of this repository are commonly active at once, each able to run a deploy against the same home. This is a live instance of dual ownership, not a hypothetical.
- **The zero-writer window**: Gating legacy writers off a domain before the new pipeline claims it (FR-027) deliberately leaves that domain with **no** writer for the duration. If the first APM deploy stalls — a failed publish, a rejected package, a NO-GO discovered late — the domain becomes un-updatable by any mechanism until someone intervenes. An explicit un-gate/abort procedure MUST exist and be reachable without reversing the migration (FR-039).
- **Retained user-edits become silent drift**: If retention is only visible via a separate audit command rather than in the deploy workflow, this feature trades loud drift for quiet drift (FR-005).
- **Pre-1.0 dependency breaks**: Roughly weekly releases; a minor release may change install or compile semantics mid-migration. Version pinning and deliberate, verified upgrades are required.
- **The build tool binary is itself untrusted code**: `apm` writes hooks and MCP server definitions into five home trees. Hooks execute shell commands; MCP entries spawn long-lived processes with tool access. This is code execution, not inert configuration, and it applies **even if the build resolves nothing remote** (FR-029).
- **Registry and naming attacks**: Publishing and installing by name introduces typosquatting, dependency-confusion, and registry-account-compromise risks that a local clone did not have (FR-018).
- **Offline / air-gapped setup**: If installation requires network access, provisioning a disconnected machine regresses relative to clone-and-rsync (FR-031).
- **Every edit requiring a publish**: If the only way to test a change is to publish it, iteration becomes distribution (FR-032).
- **Rollback mid-migration**: `deploy_configs()` is monolithic with no per-domain selector, so "just re-run bootstrap for unmigrated domains" is not currently possible (FR-019).
- **Non-markdown payload**: 54 top-level scripts (88 including subdirectories) and the `~/.claude/config/*.yml` files are not markdown primitives and need an explicit home or an explicit statement that coverage is partial.
- **Shared scripts couple nominally separate domains**: `git_ops.sh` is invoked by 12 skills across four proposed plugin domains; `git_platform.sh` spans two. Compartmentalization that ignores this is either broken on partial enablement or cosmetic (FR-028).
- **Skill-catalog budget is unaffected by US1–US3**: This must not be claimed as a benefit of the deploy migration.

## Requirements *(mandatory)*

### Functional Requirements

**Feasibility gate (blocking)**

- **FR-001**: No Manifest source, generator, or deploy path may be modified before the spike records a GO decision. A task MUST verify this held (a diff against the pre-spike tree), rather than relying on instruction alone.

  **One carved-out exception**: the publish gates (FR-030 scan, FR-038 provenance, FR-018 install integrity) MUST exist before the spike publishes its throwaway package, so they necessarily land pre-GO. They are permitted because they are **additive, self-contained, and independently valuable** — they modify no existing generator or deploy path, and they remain correct and useful under a NO-GO, since any future publishing of anything needs them. The FR-001 verification task MUST assert that these are the *only* pre-GO additions and that no existing file was touched. Nothing else may claim this exception.
- **FR-002**: The spike MUST empirically determine, in an **isolated `HOME`**, whether installing Manifest's **published** package at user-global scope deploys **file primitives** — skills, agents, and hooks **reported separately per primitive type**, not as an aggregate — to user-level harness directories. The published documentation is clear on this point; the risk being tested is **documentation/behavior mismatch on a fast-moving pre-1.0 tool**, not textual ambiguity. Documentation therefore MUST NOT be accepted as the evidence of record.
- **FR-003**: The spike MUST produce a written decision record: GO or NO-GO, per-primitive-type results, the observed behavior justifying the verdict, and the exact tool version tested.
- **FR-035**: The spike rig MUST be validated before its results are trusted: (a) a **sentinel check** proving the tool's writes are actually redirected away from the real home — the real `~/.claude` MUST be hash-identical before and after a sandboxed run — and (b) a **known-good control case** the rig demonstrably detects, so operator or rig error cannot masquerade as a NO-GO.

**Drift elimination (the core outcome)**

- **FR-004**: Deploying a migrated domain MUST remove files that a previous deploy of that domain wrote and the current source no longer produces, with no separate reconciliation step.
- **FR-005**: Deploying MUST NOT overwrite a deployed file the user has modified; such files MUST be retained, **surfaced within the deploy workflow itself**, *and* **reported as drift by the drift-detection command** (FR-008). Both channels are required: Constitution I holds that a preserved manual edit is drift, so a deploy-time warning that never reaches the drift report leaves the deployed tree permanently divergent from source with nothing tracking it. If the tool only surfaces retention via a separate audit command, that command MUST be wired into the deploy path so retention is never silent.
- **FR-006**: Re-running a deploy with unchanged sources MUST produce a byte-identical home tree and report no changes.
- **FR-007**: A clean machine MUST reproduce the full home tree for migrated domains from the published package plus committed lockfile alone.
- **FR-008**: A drift-detection command MUST report divergence between the deployed tree and the lockfile, superseding the bespoke reconciliation script for migrated domains.
- **FR-036**: Drift verification MUST include at least one check **independent of the build tool** — the lockfile is generated by the tool and the audit command reads it back, so the two are one trusted party checking its own work. An external hash of the deployed tree, computed by something the build tool does not control, MUST be a standing gate.

**Single-source builds**

- **FR-009**: Every **per-harness** output for a migrated domain MUST be produced by a single build from a single source tree, with no hand-run generator. Documentation-index generation is explicitly excluded (see FR-037).
- **FR-010**: Before a legacy generator is deleted, its output and the new build's output MUST be shown equivalent for identical input on **two independent clean runs**, where "independent" means fresh scratch directory, fresh clone, and no shared build cache. Intentional differences MUST be enumerated in writing. A static diff alone is insufficient: at least one output MUST be **functionally consumed by its real harness** before deletion.
- **FR-011**: Harnesses excluded from the build tool's default target set MUST be named explicitly so no supported harness silently receives nothing.
- **FR-012**: Derived artifacts that become build outputs MUST be removed from version control, and hygiene gates updated so their absence does not fail verification.
- **FR-037**: `generate_commands_doc.py` MUST remain on the legacy pipeline; no equivalent exists in the build tool's target matrix. This MUST be stated in the documentation rather than left as an apparent omission.

**Boundary and coexistence**

- **FR-013**: `bootstrap.sh` retains sole ownership of CLI installation, authentication, MCP configuration, service toggles, and the settings merge; it MUST NOT deploy configuration content for any migrated domain.
- **FR-014**: At every point in the migration, each deployed path MUST have exactly **one** writer, verified **including at the first moment two pipelines are simultaneously live**, not only at deletion points.
- **FR-027**: Before the first APM-managed domain ships, **every legacy writer of that domain MUST be gated off it** — `deploy_home_skills()`, `sync-skills.sh`, and any other path-writing routine. Gating MUST be per-domain, so unmigrated domains keep working. A gated writer MUST **report that it skipped a domain** rather than silently no-op, or contributors will read silence as success.
- **FR-039**: A documented, tested **un-gate procedure** MUST return a gated-but-not-yet-migrated domain to the legacy writer, so the zero-writer window is recoverable without reversing the whole migration. It MUST be usable while the migration is still in progress — not only as part of the full rollback (FR-019).
- **FR-015**: The environment diagnostic MUST report which pipeline owns each deployed area and flag any area claimed by both. It MUST exist **before** the coexistence window opens, not after it closes.
- **FR-016**: Optional components gated by service toggles MUST remain **absent** from the home tree when disabled.
- **FR-017**: The build tool version MUST be pinned, and an upgrade MUST re-run the equivalence and idempotence checks — enforced by a gate, not by documentation alone.
- **FR-019**: A rollback MUST exist and be proven, which requires a **per-domain selective deploy capability** in the legacy path; the current monolithic deploy cannot redeploy only unmigrated domains.
- **FR-020**: Non-markdown payloads MUST either be given an explicit home in the new layout or be documented as remaining on the legacy pipeline, with the resulting partial coverage stated plainly.
- **FR-021** *(superseded 2026-07-27 by FR-021a)*: ~~The existing skills source
  of truth and its external lifecycle tooling MUST continue to function; no
  third physical location for skills.~~
- **FR-021a**: `.apm/skills` becomes the **sole** physical source of truth for
  skills. The `.skillshare/` tree and the skillshare lifecycle (`install`,
  `audit`, `check`, `update`) MUST be removed, not merely bypassed. The
  migration MUST NOT leave two physical skill locations at any commit that
  ships: either `.skillshare/skills` is still authoritative, or it is gone.
  Every consumer resolving `.skillshare/skills` MUST be repointed in the same
  change that moves the tree — at minimum `command_catalog.py`
  (`COMMAND_CATALOG_SKILLS_DIR`), `generate_commands_doc.py`,
  `subagent_policy.bats`, `skill_naming.bats`, `deploy_home_skills`, and the
  `configs/claude/skills` compat symlink.
  **Feasibility measured (T005 cell i, 2026-07-27)**: apm preserves a symlinked
  target directory rather than replacing it with an independent copy, so the
  existing `~/.cursor/skills -> ~/.claude/skills` fan-out survives an APM
  deploy. That was the risk most likely to make a single-source-of-truth model
  impossible; it is cleared.
- **FR-033**: The migration MUST decide explicitly whether per-harness skill output replaces today's symlink fan-out (independent copies, per-harness divergence possible) or whether the build writes only the primary home and the fan-out survives. Either is acceptable; leaving it undecided is not. The decision MUST be justified against stated criteria: (a) whether per-harness divergence is a *feature* (harness-specific skill shaping) or a *defect* (four copies silently drifting); (b) disk and build cost of N copies of 107 skills; (c) whether the external skill-lifecycle tooling still resolves its source of truth under the chosen model; (d) which model leaves fewer paths with ambiguous ownership under FR-014.
- **FR-034**: Files mutated by Manifest's own installers MUST be distinguishable from human edits, so scripted mutation does not permanently freeze a file under user-edit retention.

**Supply chain (mandatory under the published-package model)**

- **FR-018**: Because distribution is publish-and-install, **remote resolution is inherent** and the earlier "prefer no remote dependencies" default is void. **Scope: packages and the registry** (the build tool's own binary is FR-029). Installation MUST verify package integrity (hash or signature) and MUST fail closed when it cannot. This verification MUST be **active from the first install of any package, including throwaway packages during the spike** — a gate that arrives after installs have begun protects nothing. Controls against typosquatting, dependency confusion, and registry-account compromise MUST be written into a named artifact — the **threat-control section of `decision-record.md`** — and each MUST name the mechanism that enforces it. All of this MUST be enforced by an automated gate, not by end-of-project inspection.
- **FR-029**: The threat model MUST state explicitly that deployed hooks and MCP server definitions are **code-execution primitives**. **Scope: the build tool's own binary** (packages and registry are FR-018) — its install channel MUST be integrity-verified by checksum or signature, independently of any package it resolves.
- **FR-030**: Published content MUST be scanned for secrets, credentials, machine-local paths, and private material **before** publication, with the scan **blocking** on findings. The scan MUST gate **every** publish, including throwaway or spike packages: publication is irreversible, so a leak from an experiment is as unrecoverable as one from a release. No publish step may be scheduled before this gate exists.
- **FR-038**: Every published artifact MUST be built from **committed sources at a tagged version**. Publishing from a dirty working tree, from an untagged commit, or from any state that cannot be reproduced from version control MUST be blocked by an automated gate. *(Implements Constitution VII.1, which had no requirement carrying it.)*
- **FR-031**: A documented path MUST exist to install from a pinned local artifact without network or registry access.
- **FR-032**: Contributors MUST be able to build, deploy, and test changes locally **without publishing**.

**Verification**

- **FR-022**: All deploy verification MUST run against an **isolated** `HOME`/target. *(Scope note: FR-022 governs **which environment** verification runs in; FR-035a governs **proving that isolation actually holds** for the build tool's writes. They are deliberately separate — the first is a policy, the second is the check that the policy is not silently violated. Neither is redundant, but any future edit must keep the distinction.)*
- **FR-023**: FR-004 – FR-007 MUST each be covered by an automated test that fails against the pre-migration pipeline. Each test MUST assert its **precondition** before its postcondition — a non-empty expected manifest before an idempotence diff, an old-file-present assertion before an old-file-absent assertion — so no test can pass vacuously.

**Distribution and compartmentalization (optional, US4)**

- **FR-024**: The packaged artifact MUST deliver the same configuration surface as a full install, and the Claude-plugin variant MUST NOT be represented as carrying settings it cannot carry (plugin `settings.json` supports only `agent` and `subagentStatusLine`; plugin-shipped agents cannot declare hooks, MCP servers, or permission modes).
- **FR-025**: Plugin output MUST be **compartmentalized by domain**: multiple independently installable, independently enable-able plugins. Every shipped skill MUST belong to **exactly one** plugin. The domain map MUST be derived by **functional analysis of the actual catalog**, not by name-prefix matching — prefix matching demonstrably fails (`a11y-audit` and `config-audit` each match two proposed domains; roughly a quarter of the catalog matches none).
- **FR-028**: The domain map MUST account for the **shared-script dependency graph**, not only skill names. Where skills in one domain invoke scripts or skills shipped with another, the plan MUST either declare the dependency explicitly or place the shared component so that partial enablement still functions. A compartmentalization in which disabling one plugin silently breaks another violates FR-025; one in which shared components are global regardless is cosmetic and MUST be described as such.
- **FR-026**: Every Manifest-published plugin name MUST begin with **`manifest-`**, applied to the plugin manifest name **and** the marketplace entry name, enforced by an automated check.

### Key Entities

- **Source primitive tree**: The single authored location for skills, agents, hooks, prompts, instructions — input to every harness build.
- **Lockfile**: The committed record of resolved content and per-file hashes making deploys reproducible and orphan removal decidable.
- **Published package**: The versioned, integrity-verified artifact machines install by name — the unit of distribution under the decided model.
- **Harness target**: A supported assistant and its home directory.
- **Ownership boundary**: The declared split between package installer (configuration content) and `bootstrap.sh` (installation, auth, MCP, toggles, settings merge).
- **Decision record**: The written GO/NO-GO output of the spike, with per-primitive-type results and tool version.

## Success Criteria *(mandatory)*

Each criterion names the evidence that satisfies it. "Migrated domains" is not a self-shrinking denominator: every criterion below is evaluated against the domain set declared in the migration inventory, and any domain not migrated is reported as such.

- **SC-001**: A clean machine reproduces the home tree for every declared migrated domain from the published package plus lockfile, in **one** command, with **zero** manual fixup steps — evidenced by a recorded transcript of that command in an isolated `HOME` and a diff against the expected manifest.
- **SC-002**: Renaming a skill leaves **zero** orphaned files or directories across every harness home the build owns, with **no** reconciliation pass invoked — evidenced by a `find`-based orphan scan whose pre-rename run asserts the old path present.
- **SC-003**: A user-modified deployed file survives every deploy in the test matrix and is surfaced in the deploy workflow output — evidenced by the test asserting both retention and the surfacing message.
- **SC-004**: Two consecutive deploys with unchanged sources produce a **byte-identical** tree — evidenced by an empty diff **plus** a prior assertion that the tree is non-empty and matches the expected file manifest.
- **SC-005**: Exactly **four** scripts are deleted, not stubbed: `generate_cursor_rules.sh`, `generate_cursor_agents.py`, `generate_cursor_mcp.py`, `deploy_reconcile.sh` — and the **109** committed `.mdc` artifacts are removed — with `bats tests/bats/` and `pytest tests/python/` still passing. `generate_commands_doc.py` is explicitly retained (FR-037); `sync-skills.sh` is dispositioned under FR-027, not counted here.
- **SC-006**: `bootstrap.sh` deploys zero configuration content for declared migrated domains — evidenced by the ownership diagnostic reporting a single writer for every path in those domains.
- **SC-007**: **100%** of deploy verification runs against an isolated `HOME`, evidenced by the sentinel check (FR-035a) showing the real home unchanged after each verification run.

The work is wiring a flag or environment variable through to the existing parameter.
- The build tool remains actively maintained; evidence basis is v0.26.0 (published 2026-07-18), repository created 2025-09-18, ~3.4k stars, 159 open issues, roughly weekly releases. **This is motivating context, not dispositive evidence** — FR-002 governs, and no documentation or issue-tracker signal substitutes for the spike.
- Pre-1.0 status is accepted as a known risk, mitigated by pinning, parallel-run, and rollback — not by assuming stability.
- The maintainer accepts an external tool on the critical path of machine setup in exchange for eliminating three recurring bug classes. **A homegrown alternative was considered and is not foreclosed**: a hash-manifest deployer of a few hundred lines could supply the same ownership property without a third-party dependency, and the build tool is a *partial* solution (it does not cover documentation-index generation, FR-037). If the spike returns NO-GO, that alternative is the natural next evaluation.
- `test-isolate-ambient`, cited as an isolation handle, was deployed-only when this spec was reviewed — a fresh clone or CI runner could not have followed a task depending on it. **Merging `origin/main` (PR #622) committed it**, so the gap is closed. It is worth recording that it existed at all: the skill was live and working on the maintainer's machine while absent from the repository, which is precisely the uncommitted-state drift class this feature exists to eliminate, occurring inside the feature's own tooling.
- **Naming — review finding accepted, prefix changed**: the prefix was originally `mkt-`. Review objected that it does not evoke "Manifest", reads as an abbreviation of "market", and would leave a user unable to tell a Manifest plugin from any other publisher's, weakening the provenance rationale the requirement exists to serve. The maintainer accepted the finding and the prefix is now **`manifest-`**, which states provenance directly. One limit survives the change and is recorded rather than claimed away: marketplace entry names are publisher-supplied strings with no documented global uniqueness guarantee, so the prefix establishes provenance **by convention, not by enforcement** — FR-026's check binds Manifest's own pipeline and cannot stop an unrelated publisher from using the same stem.
